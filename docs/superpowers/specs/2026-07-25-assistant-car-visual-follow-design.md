# 辅助车纯视觉并排跟随设计

## 1. 目标

在现有 `motor.py`、`odometry.py` 和独立跟随摄像头程序的基础上，构建辅助车第一版主控程序。

辅助车位于主车左侧，与主车同向并排。跟随摄像头安装在辅助车中间偏后位置，镜头朝右观察主车上的两个红外灯。辅助车仅使用摄像头通过 UART 提供的测量数据进行闭环跟随，不接收主车无线前馈，也不执行独立任务。

第一版需要同时保持：

1. 两车前后对齐；
2. 两车横向间距稳定；
3. 两车航向平行；
4. 目标丢失、数据异常或程序异常时立即停车。

## 2. 范围

### 2.1 包含

- 跟随摄像头 UART 数据接收；
- 六字段文本协议解析与数据合法性检查；
- 目标新鲜度和超时判断；
- 图像空间三通道 PI 跟随控制；
- `WAIT_TARGET / TRACKING / LOST_STOP` 状态管理；
- 电机速度指令输出和异常停车；
- 桌面纯逻辑测试；
- 后续实车标定所需的集中配置项。

### 2.2 不包含

- 跟随摄像头端图像识别代码；
- 主车与辅助车之间的无线通信；
- 主车速度前馈；
- 世界坐标路径规划和航点导航；
- 辅助车独立识别、接近或推动任务目标；
- 主车代码修改。

摄像头端程序继续保存在当前独立目录中，辅助车目录只实现 UART 接收端。

## 3. 文件结构

辅助车第一版只保留五个板端运行文件：

```text
辅助车/
├── main.py
├── config.py
├── follow.py
├── motor.py
└── odometry.py
```

桌面测试单独保存，不烧录到板端：

```text
辅助车/
└── tests/
    ├── test_follow_sensor.py
    ├── test_follow_controller.py
    └── test_assistant_main.py
```

文件职责如下：

- `main.py`：硬件初始化、20 ms 主循环、状态切换、单次底盘指令提交和最外层异常兜底。
- `config.py`：串口、时序、参考队形、PI、死区、方向、限幅和数据合法范围。
- `follow.py`：`FollowSensor`、`FollowController`、协议解析和角度归一化。
- `motor.py`：沿用现有电机速度闭环、S 曲线、轮速限幅和命令看门狗。
- `odometry.py`：沿用现有 IMU 和里程计实现；第一版只用于底层姿态、状态观测和调试，不参与路径导航。

状态机、安全处理和调试输出暂时保留在 `main.py`，不增加单独文件。只有在后续职责明显膨胀时才拆分。

## 4. 坐标和测量约定

沿用现有底盘坐标：

- `vx`：车体向右为正，单位 cm/s；
- `vy`：车体向前为正，单位 cm/s；
- `w`：俯视逆时针为正，单位 rad/s。

跟随摄像头继续发送原有六字段文本帧：

```text
1,mid_x,mid_y,line_angle_deg,distance_px,quality
0,0,0,0,0,0
```

字段含义：

- `found`：是否识别到有效红外灯对；
- `mid_x / mid_y`：两个红外灯中心点的图像坐标；
- `line_angle_deg`：两个红外灯连线角度；
- `distance_px`：两个红外灯之间的像素距离；
- `quality`：两个有效亮斑的像素数之和。

辅助车不依赖摄像头端内部实现，只依赖以上协议。

## 5. `FollowSensor` 设计

`FollowSensor` 位于 `follow.py`，负责串口字节流到测量事件的转换，不直接控制电机。

### 5.1 字节流处理

- 使用持久缓冲区保存跨轮询到达的半包；
- 一次轮询处理缓冲区中的全部完整行；
- 多行同时到达时按顺序解析，向上层提供有序事件列表；
- 未出现换行符的半包不视为错误；
- 缓冲区超过配置上限时清空，并报告无效数据事件；
- 支持 `\n` 和 `\r\n` 行尾；
- 不使用阻塞式串口等待。

### 5.2 数据合法性

完整帧必须满足：

- 恰好六个字段；
- 所有数值均可解析且为有限数，拒绝 `NaN` 和 `Inf`；
- `found` 只能为 `0` 或 `1`；
- `mid_x / mid_y` 位于配置的图像范围内；
- `line_angle_deg`、`distance_px` 和 `quality` 位于配置的合理范围内；
- `found=1` 时 `quality >= MIN_QUALITY`；
- `found=0` 时视为明确丢失事件，不沿用上一帧目标。

完整但格式错误、越界或质量不足的帧视为无效数据。辅助车处于 `TRACKING` 时，无效数据触发立即停车。串口完全静默超过 `CAMERA_TIMEOUT_MS` 同样触发停车。

### 5.3 输出

`FollowSensor` 向 `main.py` 提供按接收顺序排列的事件列表。每个事件属于以下类型之一：

- 新的有效测量；
- 明确目标丢失；
- 完整无效帧；
- 摄像头数据超时；
- 本轮没有新完整帧且上一测量仍然新鲜。

同一轮询中只要出现明确丢失、完整无效帧或超时，`main.py` 就锁定本周期的硬停车结果；该周期中稍后出现的有效帧不能覆盖停车事件，也不能计入重新捕获。

## 6. `FollowController` 设计

`FollowController` 位于 `follow.py`，只负责把有效测量转换成车体速度，不访问串口和电机硬件。

### 6.1 三个控制误差

```text
e_front    = mid_x - REF_CX
e_distance = REF_DISTANCE_PX - distance_px
e_angle    = normalize_line_error(
                 line_angle_deg - REF_LINE_ANGLE_DEG
             )
```

`normalize_line_error()` 按无方向直线的 180° 周期，将角度误差归一化到 `[-90°, 90°]`。

控制映射：

```text
e_front    -> vy，调节两车前后对齐
e_distance -> vx，调节两车横向间距
e_angle    -> w，调节两车航向平行
```

`mid_y` 第一版不直接参与速度控制，只用于图像范围和测量合理性检查。`quality` 只作为有效性门槛，不直接放大或缩小速度。

### 6.2 死区

每个误差先经过独立死区：

```text
abs(error) <= deadband  -> 0
abs(error) >  deadband  -> 保留超出死区的部分
```

采用连续死区，避免误差跨过阈值时输出突然跳变。例如正误差输出 `error - deadband`，负误差输出 `error + deadband`。

### 6.3 PI 控制

每个通道独立计算：

```text
integral = clamp(
    integral + error * dt,
    -integral_limit,
    +integral_limit
)

output = sign * (kp * error + ki * integral)
```

三个积分增益第一版默认均为 `0.0`。当 `ki=0` 时，对应积分保持为零，不做无意义累积。

积分规则：

- 只在收到新的有效摄像头测量时更新；
- `dt` 使用相邻有效测量的真实时间间隔，并限制在合理范围；
- 输出已经饱和且当前误差会把输出继续推向饱和时，停止该方向的积分；
- 误差进入死区时允许积分逐步清零，第一版可直接重置对应积分；
- 进入 `WAIT_TARGET` 或 `LOST_STOP`、目标重新捕获、人工停车和程序异常时全部清零。

不加入微分项。摄像头端已有 EMA 滤波，底盘端已有 S 曲线；第一版先标定方向、比例和死区。

### 6.4 方向与限幅

输出关系为：

```text
vy = VY_SIGN * front_pi
vx = VX_SIGN * distance_pi
w  = W_SIGN  * angle_pi
```

三个符号均由配置给出，现场通过低速架空测试确认，不在控制公式中临时改符号。

每个输出分别限制到：

- `[-MAX_VX, +MAX_VX]`
- `[-MAX_VY, +MAX_VY]`
- `[-MAX_W, +MAX_W]`

随后只调用一次 `motor.move(vx, vy, w)`。现有 `MotorSystem` 继续执行车体速度可行化、轮速限幅、S 曲线、PI 轮速闭环和命令看门狗。

## 7. 状态机

主控只使用三个状态：

```text
WAIT_TARGET -> TRACKING -> LOST_STOP
     ^                         |
     +---- 连续有效帧重捕获 ---+
```

### 7.1 `WAIT_TARGET`

- 启动后进入该状态；
- 电机保持硬停车；
- 控制器积分和缓存命令为零；
- 连续 `REACQUIRE_FRAMES` 个干净主循环均收到有效测量后进入 `TRACKING`；
- 默认 `REACQUIRE_FRAMES=2`。

每个主循环的重新捕获计数最多增加一次。包含丢失、无效或超时事件的循环会把计数清零，防止串口积压的多帧数据让车辆在一个周期内直接重新启动。

### 7.2 `TRACKING`

- 本周期没有任何安全错误时，使用最新有效测量更新一次 PI；
- 没有新帧但上一测量仍新鲜时，不重复积分，继续刷新最近一次安全速度命令；
- 每个主循环最多提交一次最终底盘操作；
- 三个误差均进入死区时提交零速度，通过 S 曲线正常平滑停车；
- 明确丢失、完整无效帧或超时立即进入 `LOST_STOP`。

### 7.3 `LOST_STOP`

进入状态时：

- 立即调用一次 `motor.hard_stop()`；
- 清空三个积分；
- 清空缓存速度命令；
- 清空重新捕获计数。

保持状态时不恢复旧命令。连续 `REACQUIRE_FRAMES` 个干净主循环均收到有效测量后，先重置控制器，再进入 `TRACKING`，以当前最新测量计算新的速度。

## 8. 主循环

`main.py` 使用非阻塞主循环，默认周期为 `CONTROL_PERIOD_MS=20`：

```text
轮询串口并处理全部完整帧
        |
        v
按顺序检查事件并锁定安全结果
        |
        v
更新状态机
        |
        v
无安全错误时用最新测量更新一次 PI
        |
        v
本周期最多提交一次底盘操作
        |
        v
等待至下一周期
```

摄像头有效帧预期约每 30 ms 到达。20 ms 主循环可以及时读取串口，又不会把相同测量重复积分。

底盘操作包括 `motor.move(...)` 或 `motor.hard_stop()`。同一周期不能先后提交多个相互覆盖的速度命令。

## 9. 安全和错误处理

以下情况必须立即硬停车：

- 摄像头明确报告 `found=0`；
- 完整帧格式错误；
- 数值为 `NaN/Inf` 或超出合理范围；
- `quality` 低于门槛；
- 数据超过 `CAMERA_TIMEOUT_MS` 未更新；
- UART 缓冲区异常溢出；
- 控制计算产生非有限输出；
- `main.py` 主循环抛出异常；
- 人工中止程序。

正常误差回到死区时使用 `motor.move(0, 0, 0)` 平滑停车。感知丢失和异常使用 `motor.hard_stop()` 立即清 PWM，并重置速度闭环和 S 曲线状态。

`main.py` 的硬件生命周期使用最外层 `try/finally`：

```text
初始化失败或运行异常
        -> motor.hard_stop()
        -> 停止底层 ticker（若已启动）
        -> 输出简短错误信息
```

错误输出不能阻止停车。不得静默吞掉影响车辆安全的异常。

```text
FRONT_KP

FRONT_INTEGRAL_LIMIT

DISTANCE_INTEGRAL_LIMIT

MAX_VY

```

尚未实车标定的参数必须保留保守初值，并在注释中标记为“现场标定项”。参数未标定不影响软件结构和桌面测试，但禁止直接以高速度落地运行。

## 11. 测试

所有跟随逻辑应能在不导入板端 `machine`、`seekfree` 或 `smartcar` 模块的桌面环境中测试。

### 11.1 协议和串口缓存

- 半包跨多次轮询后正确拼接；
- 一次收到多行时保留事件顺序并全部处理；
- `\n` 和 `\r\n` 均可解析；
- 六字段 found/lost 帧正确解析；
- 字段数量错误、非数字、`NaN/Inf` 和越界值被拒绝；
- 缓冲区溢出被检测；
- 中间的丢失或错误事件不会被后续有效帧覆盖；
- 同一轮询出现安全错误时，本周期最终操作仍为硬停车。

### 11.2 控制器

- `mid_x` 误差只主导 `vy`；
- `distance_px` 误差只主导 `vx`；
- 连线角误差只主导 `w`；
- 角度跨越 `90°/-90°` 时按 180° 周期归一化；
- 连续死区无输出跳变；
- 三个方向符号独立生效；
- 三个输出独立限幅；
- `ki=0` 时积分始终为零且不影响输出；
- 积分使用真实 `dt`；
- 积分限幅和输出抗饱和生效；
- 重置、丢失和重捕获会清空积分；
- 控制器拒绝产生非有限输出。

### 11.3 状态和安全

- 启动时电机保持硬停车；
- 单帧目标不能启动；
- 连续两个干净主循环收到有效目标后进入 `TRACKING`；
- 单次轮询积压多帧不会让重新捕获计数增加多次；
- 明确丢失帧立即硬停车；
- 完整无效帧立即硬停车；
- UART 超时立即硬停车；
- 重新捕获前不会恢复旧速度；
- 重捕获后使用新测量重新计算；
- 每个主循环最多产生一次底盘操作；
- 主循环异常最终调用硬停车。

### 11.4 实车验证顺序

1. 不接电机，仅观察 UART 解析和状态变化；
2. 架空车轮，分别验证 `vx`、`vy`、`w` 的方向；
3. 将三个 `ki` 保持为零，低速标定 `kp`、死区和输出上限；
4. 空旷场地低速落地，验证前后、间距和航向三个单通道；
5. 同时启用三个通道，验证并排跟随；
6. 遮挡红外灯、拔掉摄像头串口和制造错误帧，验证立即停车；
7. 只有确认存在稳定残差时，才逐步增加对应 `ki`。

## 12. 完成标准

第一版实现完成需要满足：

- 辅助车运行代码符合五文件结构；
- 摄像头端代码没有复制进辅助车目录；
- 不存在主车无线前馈依赖；
- 所有新增桌面测试通过，且现有电机、里程计和摄像头测试不回归；
- 有效目标下能够生成受限的 `vx/vy/w`；
- `found=0`、无效数据、超时和异常均能立即硬停车；
- 重新捕获不会恢复丢失前的旧命令或积分；
- 架空测试确认三个控制方向正确后，才允许低速落地；
- 所有现场标定参数集中在 `config.py`，控制逻辑中没有散落常数。
